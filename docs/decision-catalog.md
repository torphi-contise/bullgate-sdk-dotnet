# Access decision catalog

This catalog records the non-obvious adapter decisions behind
`Bullgate.Access.AspNetCore`. Source remains authoritative, but a change that
reverses one of these decisions must update this document and the corresponding
AI evaluation cases.

The catalog is intentionally limited to the Access SDK package. It does not
describe another package in this repository.

| ID | Decision | Why the condition exists | Consequence | Primary source area |
| --- | --- | --- | --- | --- |
| DOTNET-ACCESS-001 | Browser and mobile clients call the consumer BFF; only trusted server code calls Access through `IBullgateAccessClient`. | The integration credential and opaque Access bearers are server authority. | Untrusted clients receive semantic JSON and adapter cookies, never server credentials. | `BullgateAccessEndpointRouteBuilderExtensions`, `IBullgateAccessClient` |
| DOTNET-ACCESS-002 | Every outbound Access call uses the configured `bgic_` integration credential. | Access must derive trusted integration scope from authenticated server authority. | Client payloads cannot select or elevate realm or environment scope. | `BullgateAccessServiceCollectionExtensions`, `BullgateAccessClient` |
| DOTNET-ACCESS-003 | `applicationClientKey` is public and is resolved only inside the environment selected by the integration credential. | A stable build selector must not become a tenancy selector or bearer credential. | The key may appear in public client configuration but never substitutes for server authentication. | application-client configuration client and endpoint |
| DOTNET-ACCESS-004 | The adapter stores the session token in a host-only `HttpOnly` cookie. | Application JavaScript must not receive reusable session bearer material. | Session JSON is descriptive state; it cannot replace or select the current bearer. | `BullgateSessionCookie`, session BFF endpoints |
| DOTNET-ACCESS-005 | Session and AccessFlow capability use different cookies and paths. | Product-session authority and temporary flow authority have different scope and lifetime. | `bullgate.session` defaults to `/`; `bullgate.flow` defaults to `/bullgate/access/v1`; names must be distinct. | `BullgateSessionCookie`, `BullgateFlowCookie`, option validation |
| DOTNET-ACCESS-006 | Cookies are host-only because the adapter omits the `Domain` attribute. | Broad domain cookies could leak bearer authority to sibling hosts. | Deployments must preserve the intended host boundary instead of relying on a parent-domain cookie. | cookie implementations and tests |
| DOTNET-ACCESS-007 | `Secure=Always` and `SameSite=Lax` are defaults, not a complete application security policy. | Transport and request-origin controls depend on the consumer topology. | The consumer remains responsible for HTTPS, proxy correctness, CORS, origins, and CSRF defenses. | `BullgateAccessOptions`, `docs/security-model.md` |
| DOTNET-ACCESS-008 | Every presented session is introspected online. | A locally present cookie does not prove that the Access session remains active or correctly scoped. | Authentication depends on current Access state and may fail as unavailable when a trustworthy result cannot be obtained. | `BullgateSessionAuthenticationHandler`, `BullgateAccessClient.IntrospectAsync` |
| DOTNET-ACCESS-009 | Registration-purpose and product-purpose sessions are intentionally different. | Identity control does not prove completion of consumer registration. | Registration state is available through `IBullgateSessionFeature` but does not create an authenticated product principal. | `BullgateSessionPurpose`, authentication handler |
| DOTNET-ACCESS-010 | The consumer principal resolver is authoritative for the local subject and extra claims. | Bullgate identity and consumer authorization are separate ownership domains. | A null or blank local subject rejects authentication and removes the unusable cookie. | `IBullgatePrincipalResolver`, authentication handler |
| DOTNET-ACCESS-011 | Product-profile provisioning and resolution are consumer-owned extension points. | Access must not absorb product data or schema policy. | `IBullgateAccessApplication<TRegistration,TApplication>` returns the consumer-owned public profile. | `BullgateAccessContracts`, Access endpoints |
| DOTNET-ACCESS-012 | `ProvisionAsync` must be idempotent. | Registration completion and network delivery can be retried after an ambiguous response. | Repeated provisioning must return or preserve the same committed product result instead of duplicating it. | `IBullgateAccessApplication`, registration endpoints |
| DOTNET-ACCESS-013 | Identity contact and authenticator facts remain in the Bullgate session envelope. | Copying identity-owned data into the product profile creates competing sources of truth. | Email, phone, verification, and linked-provider state are not redefined as `TApplication` fields by the SDK. | session contracts, `docs/access-integration.md` |
| DOTNET-ACCESS-014 | A session newly issued during registration, login, social authentication, or terminal-flow handling is revoked when the consumer cannot establish the required product profile. | The adapter must not grant partial product access after Access authentication alone. | Missing or rejected provisioning/resolution produces an explicit failure and invalidates the unusable newly issued session. | registration, login, social, and terminal-flow endpoints |
| DOTNET-ACCESS-015 | An AccessFlow UUID is a selector, while the capability cookie is bearer authority. | Treating a public identifier as authority would permit flow enumeration or takeover. | Read and action routes require the matching host-only capability; the capability never appears in JSON. | flow endpoints, `BullgateFlowCookie` |
| DOTNET-ACCESS-016 | Flow actions forward a caller request id and exact expected revision. | Idempotency and optimistic concurrency belong to the service protocol, not UI timing. | The adapter does not invent a new revision, retry policy, or stale-action fallback. | `BullgateAccessClient.ActOnFlowAsync`, flow action endpoint |
| DOTNET-ACCESS-017 | An active flow rotates only flow authority; a terminal flow may replace session authority only after validation. | Temporary flow progress must not accidentally authenticate the product. | Active results refresh the flow cookie; accepted terminal product sessions are introspected, resolved, stored, and then clear the flow cookie. | flow endpoints and host tests |
| DOTNET-ACCESS-018 | Public application-client configuration is returned as a bounded public projection. | Public metadata must not expose the protected environment document or credentials. | Provider secrets and integration credentials never appear in the public configuration response. | application-client configuration contracts and endpoint |
| DOTNET-ACCESS-019 | Provider credentials are accepted only as operation inputs and are not returned. | Google and Apple assertions are sensitive proof material, not application state. | The BFF forwards the selected provider contract server-side and returns only the resulting session envelope or error. | social authentication and linking endpoints |
| DOTNET-ACCESS-020 | Successful upstream payloads are validated strictly. | A successful HTTP status with incomplete or unknown security state is not trustworthy. | Malformed or unusable success payloads become `BullgateAccessUnavailableException`, never partially populated contracts. | `BullgateAccessClient`, client validation tests |
| DOTNET-ACCESS-021 | Access rejection, consumer rejection, and Access unavailability are separate failure classes. | Business/protocol refusal, product policy, and transport trust failure require different handling. | Stable safe status/error/field values are preserved only for structured rejections; availability failures use HTTP 503 middleware. | exception types, endpoint error mapping, failure middleware |
| DOTNET-ACCESS-022 | Access unavailability preserves a potentially valid session cookie. | Timeout or invalid response does not prove that the session was revoked or expired. | `UseBullgateAccessFailures` returns no-store HTTP 503 without deleting the cookie. | failure middleware and host tests |
| DOTNET-ACCESS-023 | Explicitly inactive sessions and unusable local principals remove the cookie. | In these cases the adapter has evidence that the stored bearer cannot authenticate the consumer. | Later requests do not keep presenting known unusable local session state. | authentication handler and host tests |
| DOTNET-ACCESS-024 | Logout revokes remotely before deleting local cookies. | Deleting only the browser cookie would not revoke the Access bearer. | Successful revocation clears session and flow cookies; an availability failure preserves them for an honest retry. | logout endpoint and host tests |
| DOTNET-ACCESS-025 | Account deletion coordination remains consumer-owned. | Access and consumer databases do not share a distributed transaction. | The SDK can request current Access-account deletion but cannot promise atomic deletion of product data or choose the consumer retry policy. | `DeleteAccountAsync`, account endpoint, integration guide |
| DOTNET-ACCESS-026 | Account and identity operations select the session only from the trusted cookie. | A body-supplied bearer could target another identity or bypass host cookie policy. | Password, email, provider, and deletion routes cannot replace the current session through JSON. | current-identity endpoints and tests |
| DOTNET-ACCESS-027 | Access options fail validation at application startup. | Invalid endpoints, credential shapes, timeouts, or cookie names should fail before serving traffic. | Base address must be absolute; credential prefix, positive timeout, and distinct non-empty cookie names are enforced. | `BullgateAccessServiceCollectionExtensions` |
| DOTNET-ACCESS-028 | Caller cancellation remains cancellation, while adapter timeout and transport failure are availability failures. | The caller stopping its own work is different from failing to obtain a trustworthy Access result. | Cancellation handling and retry decisions can preserve the original cause instead of flattening every interruption. | `BullgateAccessClient`, client tests |
| DOTNET-ACCESS-029 | Package version, BFF route version, and AccessFlow protocol version are independent. | Binary compatibility, consumer HTTP compatibility, and service protocol negotiation change on different schedules. | `/bullgate/access/v1` and protocol version `1` do not imply package version `1.0.0`. | `BullgateAccessDefaults`, project metadata, compatibility guide |
| DOTNET-ACCESS-030 | The SDK has no standalone runtime or deployment. | It is a library boundary embedded in the consumer backend. | Source visibility or package availability never proves that an Access service or consumer deployment exists. | `docs/architecture.md`, `docs/project-status.md` |
| DOTNET-ACCESS-031 | Generic registration and application types belong to the consumer contract. | The SDK cannot define compatibility for a consumer's private schema. | The same generic types must be used consistently when registering and mapping Access, and consumer schema changes may break that consumer independently. | service registration, endpoint mapping, compatibility guide |
| DOTNET-ACCESS-032 | Cookie mutation and availability responses are non-cacheable. | Authentication state or sensitive failure responses must not be replayed from intermediary caches. | Cookie writes/deletions and mapped availability failures set no-store response headers. | cookie implementations, failure middleware, tests |
| DOTNET-ACCESS-033 | Public source, local version, CI artifact, registry package, hosted service, and production integration are separate evidence states. | Conflating them produces false availability and compatibility claims. | Assistants must retrieve project status and exact release/deployment evidence before saying that something is published or live. | `docs/project-status.md`, release and compatibility guides |

## How to use this catalog

When reviewing an Access adapter change:

1. identify the protected ownership, security, compatibility, idempotency, or
   failure invariant;
2. link it to an existing decision or add a new decision id;
3. verify the current source and tests rather than treating this catalog as
   executable truth;
4. update the affected canonical document and XML documentation;
5. add or revise an AI evaluation case when the answer-visible contract changes.

Do not add decision ids to every source line. Use them where a maintainer could
otherwise remove a condition as redundant and break a non-local contract.
